# Production release plan

Status: exact-manifest/runtime hardening in progress, **not production-ready**. Last reviewed 2026-09-23.
The continuation prompt is [production-goal.md](production-goal.md).

## Decisions and evidence

1. General automatic approval requires exact equality with `compatibility/manifest.json`, embedded in the executable. The manifest currently has no certified targets. The old `automatic` setting has strict semantics; a capability probe cannot enable a version. Unsupported installations use ordinary Codex with broker credentials removed. Runtime admission now binds architecture, exact OS build/distro, explicit sandbox implementation, foreground launch surface, protocol, tool, native executable, bundled helpers/resources, launcher and package digests. Windows shim behavior and effective managed-policy behavior still require native qualification.
2. The only historical positive entry is Linux/local CLI/Codex 0.151.0. It is not fresh qualification of this implementation. Windows 0.156.0 is unverified: the user reproduced elevated sandbox runtime validation failing on a 283-character directory path, including without the wrapper; the unelevated `Get-Location` test succeeded. The underlying Windows API error was not captured. Do not describe the root cause as a proven long-path bug or a proven update regression.
3. Installation preserves sandbox configuration by default. `-WindowsSandbox unelevated` explicitly enables the previously requested workaround and retains it on subsequent default reinstalls. The runtime launcher never edits settings. The TOML editor handles quoted/dotted keys, inline tables, multiline strings, unrelated arrays, backups and repeated application. It now rejects hardlinked/reparse-point config files, redirected directory chains and oversized input before rewriting; Windows hardlink and junction regression cases are prepared but have not run natively. A Linux artifact installer stages an expected-digest executable, verifies embedded/source manifest equality and execution health on both new and identical installs, selects immutable releases with atomic links, and supports rollback and uninstall in a private install directory. Install, rollback and uninstall journals finish interrupted pointer changes on the next invocation. It has passed local disposable lifecycle and bounded staged-copy write-failure tests, not a consumer release or actual disk-full rehearsal. A separate Windows artifact installer now stages exact expected-digest bytes under `LOCALAPPDATA`, checks the manifest and execution health, and uses a same-volume replacement with a recovery journal and rollback state. Its native ACL, lock, replacement and interruption behavior still needs execution and review.
4. Updates initiate discovery, candidate testing, repairs and review. They never automatically broaden the allowlist. General code repair cannot be guaranteed by a version bump. A repair agent must work on a candidate branch, have bounded authority, and pass the same evidence gate as a human change.
5. "Everyone can use it" means a public product with an explicit supported matrix and a clear unsupported response. It does not mean untested platforms become supported. No finite test suite proves every conceivable edge case; complete the matrix below and document residual limits.

## Research and design basis

- OpenAI documents `PermissionRequest` decisions and the normal approval flow when no hook decides. Tool inputs differ; a shell example does not establish edit/MCP compatibility. [Official hooks documentation](https://learn.chatgpt.com/docs/hooks)
- Elevated and unelevated Windows sandboxes have different isolation mechanisms. The latter is a documented fallback, not a universal installer default. [Official Windows sandbox documentation](https://learn.chatgpt.com/docs/windows/windows-sandbox)
- Windows capability probes and isolated verification now create children suspended, assign them to a kill-on-close Job Object, verify and resume the sole initial thread, and terminate the job before evidence inspection. This avoids the running-child assignment gap while retaining stable Rust `Command` argument, environment and stdio handling. A native Windows descendant test is prepared but unrun; job nesting, thread enumeration, installer shims and abrupt parent termination still need native execution and independent review. [Job assignment and child inheritance](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-assignprocesstojobobject), [ResumeThread](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-resumethread), [Thread32First](https://learn.microsoft.com/en-us/windows/win32/api/tlhelp32/nf-tlhelp32-thread32first)
- Repository webhooks need owner/admin access. We cannot install an upstream webhook in `openai/codex`; a scheduled release-API watcher is the available mechanism. [GitHub webhook permissions](https://docs.github.com/en/webhooks/using-webhooks/creating-webhooks)
- Schedules run from the default branch, can be delayed/dropped and can be disabled after repository inactivity. Use manual dispatch plus external heartbeat monitoring; do not advertise instant or guaranteed update detection. [GitHub workflow events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)
- GitHub's latest-full-release endpoint provides the most recent non-prerelease, non-draft release by commit creation time, which may not be the greatest numeric version. Discovery now scans a bounded release history back to the checked-in baseline on every poll, validates that baseline and the latest pointer, and queues all newer stable versions in numeric order. One version without a prior same-repository PR is opened per poll; closed PRs remain maintainer decisions, while open PR candidate files are rechecked against current official asset and npm identities. A missing baseline, exhausted scan, changed identity or incomplete native asset fails for manual recovery. Candidate runners refresh their selected version through the exact release-by-tag endpoint. [GitHub releases API](https://docs.github.com/en/rest/releases/releases)
- The 0.156.0 release's `target_commitish` is `main`, so it cannot identify the source used by the repair worker. Its actual ref points to an annotated tag object, which points to a commit. Schema-3 candidate records now pin both SHA-1 object IDs; discovery, open-PR checks and candidate runners refresh them through the official Git reference and tag-object endpoints. The repair worker compares both IDs with its checkout before inspecting upstream source. This detects a moved or deleted ref, but does not prove the tag was signed or that the released binaries were built from that commit. [Git references API](https://docs.github.com/en/rest/git/refs), [Git tags API](https://docs.github.com/en/rest/git/tags)
- Token-created PR checks can require workflow approval. Candidate probes run in the watcher workflow itself; reviewed code changes still need full PR CI. [GitHub workflow triggering](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow)
- npm lockfiles record resolved tarballs and integrity values. The watcher now records the exact parent and native-alias identities, checks the complete generated lock, uses `npm ci` without package scripts, and requests registry signature and provenance verification before non-live probes. This checks the candidate's npm supply chain, not this project's final binary provenance or PermissionRequest behavior. [npm lockfiles](https://docs.npmjs.com/cli/v11/configuring-npm/package-lock-json/), [npm signature audit](https://docs.npmjs.com/verifying-registry-signatures/)
- Workflow actions are pinned to commit IDs read from their upstream repositories. Repository protections and independent review remain necessary. [GitHub Actions security](https://docs.github.com/en/actions/reference/security/secure-use)
- Configuration editing uses a TOML parser that preserves comments and formatting rather than interpreting configuration as lines. Some formatting may normalize; the original is backed up exactly. [toml_edit documentation](https://docs.rs/toml_edit/latest/toml_edit/)
- Windows `File.Replace` supports same-volume replacement with an optional backup. It can fail when the destination is held without delete sharing; the artifact installer retains its journal for the next invocation in that case. Windows filesystem and ACL behavior must be tested natively before relying on the prepared lifecycle. [Microsoft File.Replace documentation](https://learn.microsoft.com/en-us/dotnet/api/system.io.file.replace?view=netframework-4.8.1)

## Implemented in this worktree

- Exact manifest admission at launch and runtime request handling. Historical Linux 0.151.0 authority is removed. Historical `automatic` flags/environment values cannot bypass it. Full tuple equality is enforced by the release gate; source hashing includes the manifest.
- Separate, exact-command-only experimental verifier; no candidate can gain general approval through verifier metadata. The verifier consumes at most one allow. Both brokers count connections before parsing and audit every parsed request before deciding it, so malformed broker frames, denied requests and replays fail its one-request check. Audit event names use fixed labels to prevent log injection. Brokers bind the first accepted session, consume each hook process identity once, reject duplicate request content and cap their ledger. A bounded `codex exec --json` trace inspector now rejects missing, additional, altered and failed command executions without trusting the agent's final message; it is not connected to a live harness or the release gate. The inspected Codex 0.156.0 headless exec source forces approvals to `never` unless the reviewer is auto-review. A proposed headless verifier was therefore withdrawn: it would either miss `PermissionRequest` or broaden approval authority. Malformed inputs that never connect to the broker and an independently witnessed command outcome still need durable native evidence; the interactive live harness needs current CLI adaptation. [Codex non-interactive JSONL documentation](https://learn.chatgpt.com/docs/non-interactive-mode), [inspected upstream exec source](https://github.com/openai/codex/blob/rust-v0.156.0/codex-rs/exec/src/lib.rs)
- Manual fallback removes inherited token, socket, protocol and audit variables. Native admission hashes and holds the executable; Linux launches via the held descriptor, Windows denies write/delete sharing, and both brokers recheck running-image identity. Windows directory owner/DACL and reparse-point admission now cross-compiles but has not run natively or received independent review. Probes no longer join descendant-held output pipes. Unix probe and interactive-verifier process groups are cleaned up. Windows probe and verifier Job Object cleanup now cross-compiles and has a prepared native descendant regression, but no native execution or review.
- The Windows broker accept loop previously joined active pipe workers while reaping completed workers, delaying an independent request behind a stalled client. Both brokers now retain active workers without joining them until shutdown; a bounded cross-platform regression passes and a native Windows two-client pipe regression is prepared. The Windows broker test has only cross-compiled.
- Linux broker frame reads and writes now recompute the remaining absolute deadline for every partial transfer. A slow sender that supplies bytes just before each socket timeout can no longer extend one broker request indefinitely; a Unix-socket regression exercises a frame completed after its deadline. Native Codex approval behavior is still unverified.
- The experimental interactive verifier now creates a nonce-bound loopback HTTP witness and authorizes only its exact bounded `curl` HEAD command. It requires one broker allow and one independently received request, and rejects unexpected requests. The probe and real local `curl` pass Linux tests. It no longer bypasses Codex hook trust for all configured hooks; the exact temporary hook must undergo normal trust review. An opt-in `--diagnostic-dir` retains a redacted audit and explicitly unqualified JSON summary after the broker stops. The verifier still uses the user's authentication/configuration context and has not run a real Codex child in an eligible native terminal. It does not produce a reviewed schema-2 report or independently prove no prompt. Hook composition and an unattended isolated harness remain release blockers. [Official hook trust and composition rules](https://learn.chatgpt.com/docs/hooks)
- Ambiguous version banners rejected; documented nullable descriptions accepted.
- Explicit Windows TOML configuration command and installer switch; no blanket sandbox downgrade.
- Six-hour release polling, optional draft PR creation, native-runner synthetic tests and non-live CLI probes. The watcher uses the official latest-full-release pointer and scans a bounded history back to the previous tag on every poll. It verifies recorded prior native asset, npm and tag/source identities, then queues all newer stable versions oldest first and opens one previously unhandled same-repository candidate PR per poll; missing history fails closed. The checked-in 0.156.0 baseline is now a full, unverified schema-3 record reconstructed from current official release, npm and annotated Git tag metadata on 2026-09-23; no earlier digest history exists. Discovery retains exact official Linux/Windows asset IDs, sizes and SHA-256 digests plus SHA-512 registry integrity for the npm parent and six native aliases. Candidate runners redownload and verify native assets, check a complete exact-version npm lock against recorded registry metadata, install with scripts disabled, audit registry signatures and attestations, and probe the installed shim. Initial preflight separates official asset/CLI checks from candidate-branch Rust checks, so a download, metadata or CLI failure cannot invoke the code-repair worker. The repair job additionally requires a signal artifact emitted only when `cargo fmt`, `cargo test` or Clippy actually fails; checkout or toolchain setup failure cannot supply it. Only a newly opened candidate PR is automatically repair-eligible; later polls advance through the backlog without spending that key again, while explicit dispatch can retry an exact version. Unchanged releases skip candidate jobs and no longer require a deleted post-merge branch. A Cargo failure caused by a runner problem can still trigger an unnecessary attempt and needs workflow-run review. The watcher resolves one exact remote candidate commit; preflight, code checks and repair inspect that commit, and post-repair checks inspect the newly pushed repair commit. Candidate and post-repair checks run Rust from the candidate branch while executing metadata tools from a separate trusted default-branch checkout. Both require candidate-branch metadata to equal the freshly fetched official release-by-tag, Git-ref and tag-object record before downloading the native asset. A bounded single-attempt repair workflow is prepared: its read-only job checks the tagged upstream source against the candidate's pinned tag object and commit, then inspects it as untrusted data and emits a restricted Rust patch; a separate write-token job validates and pushes it, and read-only native runners repeat non-live checks. This workflow has not run on the default branch. Download and npm package integrity, registry signatures and repaired tests are not qualification of the approval hook or this project's final consumer binary. New metadata remains unverified. Existing open/closed candidate PRs are not overwritten. Each open same-repository PR is read-only checked against current official release assets, npm integrities and source tag identities at its pinned branch commit; a changed record or moving branch stops catch-up for manual review.
- Release policy, evidence/source integrity validation, and a manually triggered readiness workflow. A second, main-only manual workflow stages native Linux/Windows release binaries and checksums, attests the digest-checked **candidate** bytes in a protected-environment job, and separately requires each downloaded binary to pass its native release gate. Candidate provenance can precede qualification without claiming approval compatibility; the overall workflow fails until both gates pass. It has not run; see [candidate provenance](release-provenance.md). `ready: false` and outstanding blockers intentionally prevent production qualification.
- A native candidate build-input SPDX generator now filters Cargo's resolved normal/build graph for the exact Linux or Windows x86_64 host, verifies selected locked crate archives, and binds one executable SHA-256 and canonical source digest. The prepared candidate workflow stages and rechecks each SBOM with its binary, then requests a binary-subject SBOM attestation. The release gate requires a retained SPDX artifact whose consumer digest and source match the reviewed report. Local Linux generation and official SPDX 2.3 schema validation passed; no native Windows workflow or final consumer SBOM attestation has run. Compiler, standard-library and OS components, exact linked-code composition and independent dependency review remain open.
- The candidate workflow now stages a bounded native build observation with the executable and SBOM. It records exact source/binary/lockfile/manifest digests, clean Git revision, compiler/Cargo versions and selected host OS facts; native qualification rechecks its digest and toolchain match. The release gate additionally requires a retained build-record file and matching build commit in every reviewed native report. This is self-reported review material, not verified provenance, reproducibility or a linked compiler/standard-library/OS component inventory. The workflow has not run.
- The manual candidate workflow now also compares each staged native executable with two separate, offline, locked release builds of an archived clean commit and stages a source/toolchain/binary-bound JSON observation. Downloaded-artifact jobs recheck the report and its checksum. Two such Linux builds from commit `8187e42` matched byte-for-byte locally; the integrated script and the Windows path still need execution. One-host repeatability does not establish cross-host reproducibility or signed provenance.
- A Windows x86_64 artifact installer and deterministic development ZIP packager are prepared. The installer keeps digest-addressed releases and a stable executable under a caller-owned `LOCALAPPDATA` directory, rejects broad-write directory ACLs and reparse points, verifies the external expected SHA-256 and embedded/source manifest, and journals upgrade, rollback and uninstall. The prepared native Windows workflow now tests the lifecycle in PowerShell 5.1 and 7 and rehearses an exact-byte extracted ZIP install. Only syntax and archive serialization have run on Linux; these prepared Windows paths are not qualified. The ZIP and adjacent checksum explicitly state unqualified development status.
- A local `cargo-audit 0.22.2` scan against pinned public RustSec advisory-db commit `f7dc4b2860b29978f400fda0aab31cc4dbd21134` found zero vulnerabilities and zero informational warnings among all 89 locked packages. It ran offline against the cloned database, without transmitting the inventory. Yanked status, advisories outside RustSec, exact binary reachability and independent security review remain open; see [dependency review](dependencies.md).
- Dependency update configuration, pinned workflow actions and code-owner entries. These files do not enable repository rules by themselves.

## Evidence and release gate

`compatibility/manifest.json` is the single immutable production support manifest (schema 2); it is compiled into the binary and printed by `support-matrix`. `verify-manifest --manifest <path>` verifies installer equality without changing authority. `compatibility/release-policy.json` is schema 2 and intentionally remains `ready: false` with no certifications.

Retain native reports and redacted artifacts under `compatibility/evidence/`. Each schema-2 native-live report identifies the complete manifest `target` and `evidence_id`, current source digest, final consumer executable digest, upstream artifact digest, build commit, observation timestamp, producer, independent reviewer, approved review and durable HTTPS run URL. Every required check in `scripts/release_gate.py:CHECKS` must reference retained artifacts whose digests verify; the consumer SBOM, build observation and two-build reproducibility report are checked structurally against the exact source and binary. Evidence older than 30 days is rejected. The source digest covers the manifest, code, dependencies, tests, installer scripts and workflows; edits invalidate existing reports. Policy references each report by ID, path and SHA-256.

The gate compares the **whole** runtime manifest to its source, the **whole** report target to its certificate, and the inspected consumer executable digest to a native report. The consumer SBOM check must cite one retained SPDX document naming that digest, source and supported native target. Duplicate keys/tuples, incomplete targets, revocations, missing retained logs, unsupported tools, stale evidence, self-review and source mismatch fail. The gate cannot establish the truth of a report or supply the independent review; protected branches and actual native execution remain necessary.

See [hardening validation](validation-2026-09-23-hardening.md) for current check results and the requirement-by-requirement continuation ledger. None of these local synthetic checks qualifies a production target.

## Repository activation

Merge the reviewed changes to the default branch before expecting scheduled discovery. Enable Actions and permission for the bot to create PRs. Configure required code-owner review for compatibility, security, workflows and installers; disallow direct/force pushes to release branches. Set required native CI checks and protect signing/publishing environments. Verify private vulnerability reporting and establish a support/incident contact. Deploy an external monitor for watcher success if update-detection latency matters.

No workflow, repository setting, signing credential or public release was activated by preparing these files locally. Manual commands:

```sh
python -m unittest discover -s scripts -p 'test_*.py'
python scripts/watch_codex.py                         # metadata only, network read
python scripts/release_gate.py                       # structural validation
cargo test --locked --all-targets
cargo clippy --locked --all-targets --all-features -- -D warnings
cargo build --release --locked --bin codex-autoapprover
python scripts/release_gate.py --require-ready --binary target/release/codex-autoapprover
```

The last command must fail while qualification remains incomplete. A failed check is a blocker, not a reason to weaken the gate.

# Compatibility and certification

Normal automatic approval requires exact equality with a certificate in `compatibility/manifest.json`. **The current embedded manifest has no certificates.** The tuple includes version, OS, architecture, exact distro/release and build, sandbox implementation, foreground CLI surface, protocol, tool, native executable and bundle SHA-256, launch kind, launcher SHA-256 and parent package SHA-256. A prospective armed session additionally requires an explicit `workspace-write` choice and receives `on-request` approval policy for that invocation; managed-policy behavior still needs native qualification. `automatic` is now a legacy alias for `strict`; neither an environment variable nor a passing help/configuration probe can enable an unknown release. The broker independently rechecks admission and the actual running image before allowing a production request.

## Distribution metadata is not runtime authority

The distribution roadmap defines bounded release metadata and a pure applicable-release selector. A parsed release manifest is descriptive and untrusted. Its authenticated wrapper has no production constructor until the planned TUF root, role, expiry, and target verification is implemented; the synthetic constructor is only for tests. Even an authenticated release, explicit installation consent, or a successful local session cannot create a certification entry or bypass exact artifact, host, sandbox, session, process, tool, and command checks. The selector's experimental label describes metadata only: legacy `automatic` remains an alias for strict runtime admission, and the embedded certification manifest remains empty. No updater, installer, or distribution artifact is production-qualified.

`verify-local-hook` is an interactive experiment with a temporary repository. Only its broker can use the candidate schema path, and only for one generated, nonce-bound `Bash` curl HEAD probe to a local listener. It never edits the allowlist. Zero permission events, dirty state, multiple allows, missing or unexpected local requests, command mismatch, errors or incomplete cleanup are inconclusive/failing evidence. The exact hook needs normal trust review. The verifier requires a separate file-backed test login and a private temporary child home; managed requirements and hooks may still participate. An optional `--diagnostic-dir` retains a hash-only audit and an explicitly unqualified JSON summary after the broker stops; it is diagnostic material, not a schema-2 native report or independent observation.

The current release gate compares the entire embedded manifest to the source manifest and each complete target to retained native evidence. The launcher hashes native executable bytes and every file in a recognized native bundle, binds npm launcher and parent metadata bytes, holds file identity, launches the held inode on Linux, denies Windows write/delete sharing, and checks the running process image before decisions. Group- or world-writable Unix files or directory chains are ineligible; the local npm installation currently fails this check. Windows bundle admission now checks local directory owners, DACLs and reparse-point status; this code has only been cross-compiled, and native behavior and races require testing and independent review. Linux distro bytes and kernel build are bound; Windows uses the native OS version and update build revision. Known hosted/IDE/WSL/container surfaces and inconclusive host reads are unarmed. These mechanisms still require independent review and native qualification; non-npm package managers, managed-policy precedence and broader argument/profile coverage remain open. See [production plan](production-plan.md) for native acceptance criteria and required evidence.

[Release discovery](../scripts/watch_codex.py) stores unverified candidates separately. Discovery, candidate probes, code repair and certification are separate steps. No upstream announcement or automated code change can self-certify a release.

## Evidence schema

The manifest, release policy and native reports are schema 2. Policy references `{evidence_id, evidence, sha256}`; each report embeds the exact `target`, source digest (including the manifest), consumer executable digest, upstream artifact digest, build commit, producer/reviewer identities, approved review, UTC observation time and HTTPS run URL. Each required check references retained redacted artifacts under `compatibility/evidence/`, whose hashes the gate verifies. Reports are limited to 1 MiB; each retained artifact is limited to 16 MiB, with at most 128 artifacts and 128 MiB total per report. The consumer SBOM and build-record checks each require their own retained exact-byte file. The gate checks the build record's target, clean-tree claim, commit, source, binary, lockfile, manifest and bounded toolchain/host fields against the report and checkout. Evidence must be no more than 30 days old at qualification. Any source or manifest change requires a fresh report. See `scripts/release_gate.py:CHECKS` for the required results. Structural validation cannot establish truth or replace independent review.
